# 技能自身的三层结构：为什么这样分、怎么维护

> 这份文件解释 `layout-json-to-epub` 的组织方式。改动技能结构前先读它，避免把已经下沉的机制细节又写回 SKILL.md。

**通用方法已独立成技能**：`skill-library-maintenance`（量三个数 → 开关表 → 逐字搬运 → 机械防漏 → 互链进 JSON）。本文件是它在本技能上的具体落地；再改任何技能的结构，先读那个，再读这份。

## 三层各放什么

| 层 | 内容 | 规模 | 加载方式 |
|---|---|---|---|
| `SKILL.md` | 入口：8 个形态开关、唯一主线、机制篇索引、症状检索表、交付清单、案例索引 | ~7 K 字符 | 每次必读 |
| `references/mechanisms/*.md` | 按**机制**组织的判据与踩坑（跨页合并、注释体系、图题、表格公式、文件引文、结构噪声、EPUB 组装、校验、外部参照、输入协作、表题与表格断段） | 11 篇 / 12 节 / ~127 K 字符 | 按开关命中读 1–3 篇 |
| └ 每篇头部 `## 相关篇` | 该机制与哪些邻篇相交、为什么（37 条指针） | — | 顺带看一眼 |
| └ 条目下 `双归属 → **Mx**` | 跨两个机制的实测结论，正文只在主归属篇写一份（21 条标记） | — | 顺藤摸瓜 |
| `references/*-case.md` | 按**书**组织：源文件构成、已知缺陷、用户当场指出的问题、最终口径 | 17 篇 | 只读同形态那一篇的差异清单 |
| `scripts/` | 可单独运行的诊断 / 修复 / 校验脚本 + 互链表 `mechanism_links.json` | 27 个 | 直接跑，不重写 |

## 为什么改成按机制（重构前的问题）

旧版 SKILL.md 是**按书**组织的：9 个「变体」节各占一段，合计 53,219 字符 / 占全文 63%。但变体之间的差异只是参数（页数切分、注释体系、有无公式），**机制被复述了 9 遍**。实测重复次数：

| 机制 | 旧版出现在几个小节 |
|---|---|
| 跨页合并 | 16 |
| `discarded` 块处理 | 14 |
| 圈码 / 注释标记 | 11 |
| 页眉噪声 | 11 |
| 索引 | 11 |
| grid 表格 | 10 |
| 上标 | 10 |
| 封面注入 | 10 |

后果有两个：① 每次会话全读 85 K；② 改一处要同步 9 处，必然漂移。

## 重构方法（可复用）

1. **先量，再切**。统计各节字符数、统计每个机制在多少小节里出现——用数字说明「重复」而不是凭感觉。
2. **把「变体」换成正交开关**。8 个开关（公式 / 注释体系 / 重编粒度 / 表格 / 插图 / 结构 / 附属 / 多文件），每本书是一组取值；判型只问数据特征，不问书目。
3. **主线写死一次**：`探型 → extract → build → pandoc → 校验 → 交付`。所有变体都是这条线上的开关组合。
4. **分桶用「节默认 + 关键词覆盖」，然后人工复核两轮**。实测：关键词分桶只能处理 263/402 条，其余需人工判；自动结果里约 25 条跨篇错位（「注释篇里混标题层级」「校验篇里混 pandoc」），两轮修正共移动 49 条。**不要指望一次分对。**
5. **逐字搬运，不改措辞**。保留实测数字与原节出处，每篇按来源节分组（`## 来自「…」`），便于回溯。
6. **机械核对收尾**：`scripts/verify_skill_migration.py <旧SKILL.md> <技能目录>`，抽出旧版全部行首加粗结论逐条比对，**0 丢失**才算完成。上一次基线：298 条结论、392 条条目（含 35 条互链指针 + 21 条双归属标记）。

   **「结论条数」那个数字会随喂进去的文件而变，不要当回归判据**：拿现版 SKILL.md 当旧版喂进去只报「13 条结论 / 570 条目」（旧基线 298 条来自重构前 85 K 的那版），照样是合法的「未找到 0 条」。判据只有两条：`未找到 0 条` + `机制篇条目合计` 与实算相符。

## 维护规则

- **新学到的东西先判归属**：换本书还会踩 → 追加到对应机制篇末尾；只在某本书成立 → 进该书 case。**不要往 SKILL.md 加机制细节**，那是它膨胀到 85 K 的原因。
- **一条结论可能双归属**（例：「合并后圈码标记挂到错误页底注」＝跨页合并的连带故障 + 注释配对问题）。放主归属那篇，在另一篇对应位置加一行「双归属 → **Mx**」指针，**不要两处各写一份**。
  - 已实现（21 条双归属标记 + 37 条相关篇指针）：每篇头部有 `## 相关篇` 列出该读哪些邻篇、为什么；具体条目下方有 `- 双归属 → **Mx**（原因）`。
  - **这些互链写在生成脚本里，不在 md 里**——`references/mechanisms/*.md` 是生成产物，手改会被下次重新生成覆盖。要改互链，改 `REL` / `DUAL` 两张表（见 SKILL.md 维护说明），再重跑生成。
- **改开关表要检查「必读篇」是否仍被覆盖**：M2（跨页合并）/ M8（组装）/ M9（校验）是主线必经，必须无条件读；它们不由任何开关决定。首次重构时就漏了这一条——按开关推演会以为「没有插图就不用读 M4」成立，但没人保证必读篇会被读到。
- **新增机制篇**时同步改三处：`SKILL.md` 的机制篇索引表、症状表里至少一行指向它、本文件的表格。
- **大改结构前先给骨架提案**（分层方案 + 体积预估 + 防漏办法），用户确认后再动手。用户明确要求过「先做一份新骨架给你看」——不要直接开搬。

## 脚本可移植性审计（哈维案例实测，必做）

技能自带的 27 个脚本**默认不可移植**。不要读代码判断可不可用——拿一本新书的数据全部跑一遍，看崩在哪、报什么。实测分三层：

| 层 | 数量 | 判据 | 换书要做什么 |
|---|---|---|---|
| **成品级** | 10 | 吃 `book.md` / `.epub`，与中间层 schema 无关 | 直接跑 |
| **常量绑** | 6 | 算法通用，但内含书名 / 章节名 / 小节名常量 | 改常量 |
| **路径绑** | 2 | 写死 `/root/hegel_yizhu/pages.json` | 传 argv（已改成接参数，缺省回退旧路径） |

- 成品级：`validate_epub` `check_grid_tables` `check_tables_pandoc` `check_figure_pairing` `check_quote_paragraphs` `check_end_matter_and_loss` `fix_epub_links` `wrap_math` `blind_read_quotes` `dump_insert_context`
- 常量绑：`align_marks_notes`（章节名表）`diag_two_note_systems` `reflow_inserts`（术语表排除规则）`html_table_to_grid` `check_caps` `rebuild_panels`

**根因是中间层 schema 三套并存**（`body`/`blocks`、`type`/`t`、`text`/`s`）。契约表见 SKILL.md「pages.json 契约」。新项目 extract 时同时写两套别名，能省掉一轮「崩→改→再崩」。

**「跑通了」不等于「结论对」。** 假警报比崩溃更危险——它会让 agent 去改一张本来正确的表。审计时两个真 bug 都是这样暴露的：

| 脚本 | 症状 | 根因 |
|---|---|---|
| `check_grid_tables.py` | 一张 pandoc 渲染正常的表被报 17 处「行宽不对齐」 | 用**字符偏移**比对竖线，而 grid table 按**显示列宽**填充（中文占 2 列）→ 改 `dw(行前缀)` |
| `check_caption_completeness.py` | `KeyError: 'type'` 直接崩 | 只认 `type` 不认 `t`；块类型名只认 `fig` 不认 `image`/`chart`；题注字段只认 `cap`/`fnote` |

**交叉验证是抓假警报的最快手段**：`check_grid_tables` 报问题而 `check_tables_pandoc` 报 0，且表里有中文 → 先怀疑前者，别去改表。

## 改完必须回归

拿一本**已交付过**的书（有 `book.md` + `final.epub` + `pages.json`）跑全部脚本，对比改动**前后输出的差异**。只看 exit code 不够：

- 本次 `check_grid_tables` 修前修后 exit 都是 0，差别在「问题 17 处」vs「问题 0 处」
- 管道会吞掉 exit code（`cmd | tail` 报的是 tail 的退出码）——要判成败就别接管道，或读 `${PIPESTATUS[0]}`
- 修完假警报还要**反向验证没把真问题一起关掉**：故意造一个坏样本（如列宽不足的中文表），确认脚本仍然抓得到

## 发布到 GitHub

- 仓库 `MaplumeX/hermes-epub-skills`，本地克隆在 `/root/skills_upload/hermes-epub-skills`（`~/.hermes/skills` 本身不是 git 仓库，直接在那儿 `git status` 只会报 not a repository——先找克隆，别以为没仓库）
- 流程：同步 → 删 `__pycache__` / `*.pyc` → `git add -A` → commit → push
- **同步用 Python `shutil.copytree(src, dst, dirs_exist_ok=True)`，不要指望 `rsync`**（这台机器没装，`FileNotFoundError: 'rsync'`）；`cp -r src dst` 在 dst 已存在时会把源**嵌套**进去（`dst/layout-json-to-epub/layout-json-to-epub`），别用。同步完必须 `diff -rq <live技能> <仓库副本> -x __pycache__` 输出为空（等价 IDENTICAL）才算干净

### 发布前必做：内容丢失体检（用户说「推送更新」时最容易踩）

**用户只说「提交推送」时，不要直接 `cp -r` + commit**——本地技能目录是各会话直接改的，同步会把丢失一起推上去。按顺序做：

1. `diff -rq <live技能> <仓库副本>`，逐条看：新增文件（真新内容）、修改文件（要看 diff，不只看文件名）。
2. **每个被整篇重写的机制篇都要看 H1 标题是否变了**：新机制若被写到**已有文件名**上（例：把「文件引文 M13」写进 `mechanisms/quotes.md`），旧机制（M6 引文段判定，7 条结论）会被**整篇覆盖**且 diff 只显示「内容不同」，不会报「删除了 7 条」。本会话就是这么丢的：SKILL.md 索引还指着 M6，文件里已全是 M13。
3. 发现覆盖时**先补回再推**：从仓库副本取旧文，接在新内容前面，文件头加一句「本文件含两部分：M6（…）与 M13（…），按书的类型只读对应部分」，两部分各保留一个 `# Mx` 标题。然后跑 `scripts/verify_skill_migration.py <仓库里的旧 SKILL.md> <live技能目录>` 确认「未找到 0 条」。
4. **同一仓库里的另一个技能（`web-to-epub`）也 diff 一遍**：只推 `layout-json-to-epub` 会让仓库与本地长期不一致，而且那半边往往也有未推的改动（本会话 5 个：封面取扫描页、文本保真校验、marxists 版式差异）。

### 索引与计数要一起改（数字实算，不抄旧值）

新增机制篇后，**同一个数字散落在五处**，漏一处就自相矛盾：

| 位置 | 要改什么 |
|---|---|
| `SKILL.md` 机制篇索引表 | 新行：M 号 + 文件名（同文件写「同文件后半」）+ 什么时候读 + **条目数（实算 bullet 数，扣掉 `## 相关篇` 里的指针）** |
| `SKILL.md` 结构段 | 「11 篇 / 12 节」这类总数 |
| 本文件三层表格 | 篇数 / 节数 / 字符总量 / `*-case.md` 篇数 / 脚本个数 |
| `README.md` 结构树 | `# N 篇机制（约 X K 字符）`、`# N 份案例`、`# N 个脚本` |
| `README.md` 机制表 + `### N 篇机制` 标题 | 新机制行与标题里的数字 |

计数一律实算：`ls scripts/*.py | wc -l`、`ls references/*-case.md | wc -l`、机制篇字符和用 Python 求和。本会话 README 的「10 篇 / 17 份案例 / 25 个脚本」全是旧值（实为 11 / 17 / 27），照抄就会写错。

**条目数会长期漂移，每次推送重算全部 12 行，不要只改新增那一行。** 机制篇是「往末尾追加」的维护方式，条目数没人跟；某次推送前实测索引 M3 写 89 而实算 164、M8 写 26 而实算 49，M1/M2/M4/M5/M7/M9/M13 同样低报。实算口径（已复核：M6 的 7、M10 的 16、M14 的 6 本来就对，说明口径正确、只是数字旧）：

- 按 `## ` 切节，**丢掉 `## 相关篇` 整节**，数剩下的 `- ` 开头的行
- `mechanisms/quotes.md` 一个文件装两篇：在 `\n# M13` 处切开，前半归 M6、后半归 M13
- 12 个条目数相加 ≈ `verify_skill_migration.py` 报的「机制篇条目合计」（差值正是被丢掉的 37 条相关篇指针：533 + 37 = 570）
- 机制篇字符总量同步改（本会话 110 K → 127 K），三处都写：SKILL.md 结构段、本文件三层表格、README 结构树

**README 不在技能目录里，`diff -rq` 查不到它**——提交前单独读一遍仓库根 `README.md`，核结构树三个数字 + 机制表 12 行条目数 + `### N 篇机制` 标题；新增了 `references/` 根目录的方法篇（`endnote-stream-parsing.md`、`missing-marks-recovery.md` 这类不带 `-case` 的）时，在 README「关键内容」补一行指针。

- **`apply_mechanism_links.py` 只重注入 `## 相关篇` 与 `双归属` 行，不重建正文**：所以手工补回的正文不会被它冲掉；但新增或改名机制篇时要同步 `scripts/mechanism_links.json` 的 `FNAME`，否则该篇互链不再被维护。
- **gh 默认活动账号是 rualons，推这个仓库必须显式指定**：`GH_TOKEN=$(gh auth token --user MaplumeX) git push origin HEAD`（rualons 对该仓库只有 `pull`，本就推不动；`gh auth status` 里显示的 active 账号不代表这次 push 用了谁）
- **commit 作者邮箱必须写 `MaplumeX@users.noreply.github.com`（大小写跟登录名一致）**：GitHub 按**邮箱**归属作者，小写 `maplume@users.noreply.github.com` 命中另一个真实账号 `Maplume`（id 141901647），推送成功但提交显示在那个账号下。历史提交用 `git log --pretty='%an <%ae>'` 对照，新提交邮箱与它们不一致就是冒烟点；写错了用 `git commit --amend --reset-author --no-edit` + `git push --force-with-lease` 修
- **推之前跑格式体检**：`python3 scripts/check_skill_format.py <技能目录> ...`（查 name 与目录同名、description ≤1024 与「何时用」、标准外字段、正文 token 估算、scripts 语法）——`exit 0` 才推；它只认 Agent Skills 标准，不认 Hermes 私有字段。
- **frontmatter 保持通用**：只写 `name` / `description` / `license` / `compatibility` / `metadata`（Agent Skills 开放标准）。不写客户端私有字段（如 Hermes 的 `platforms:`）——写回去会让其他客户端忽略或报错；宿主专有差异统一写在 SKILL.md「宿主适配」一节。
- 推完核远端，别只信 push 的输出：`git ls-remote origin master` 对 SHA、`gh api repos/MaplumeX/hermes-epub-skills/contents/<path> --jq '.size'` 对文件大小、目录用 `--jq 'length'` 对数量、`gh api repos/MaplumeX/hermes-epub-skills/commits/<sha> --jq .author.login` 对作者归属

## 案例：哈维《资本的限度》的引文判定四轮演进

这条演进过程说明了「为什么不能靠正则」：

1. 第一轮：`段末有出处` 单条正则 → 77 个候选里只有 57 个是整段引文，另 100 个是作者分析段、20 个是段末引语，误伤 120 处。
2. 第二轮：显式 `QUOTE_STARTS` 白名单（人工读 163 个候选段后写死）。
3. 第三轮：「前段未结句就并入」的自动扩展 → 把作者引导句吞进引用块，用户直接说「v3 错了 撤回」。
4. 第四轮（定稿）：**逐章盲读 + 并行 subagent**——按章拆文件、剥掉全部 `> ` 标记、段落顺序编号，一个 subagent 读一章只回段号，回来映射成段首指纹。89 段 → 84 个引用块（5 个跨段）。

**关键教训：必须盲读。** 带着已有 `>` 标记去读，模型只会核对已有标记——第一批 8 章（含标记版）报出 0 处漏判、1 处误判，全是照抄旧结论；剥标记重派后同一批章补出 20 余段。详见 `mechanisms/quotes.md` 与 `scripts/blind_read_quotes.py`。
